Your turn

Copy a prompt, paste it in, change the bits in brackets. The goal is not a good tool — it is one thing you changed, working, in front of you.

Everyone, first

Make it yours — ninety seconds

Download maths-tool-starter.html, open it so you have seen it work, then drag the file into a new Claude or ChatGPT chat and paste this.

This is my starter file. Read the brief in the comment at the top and follow those rules.

Change the --brand colour to [a deep purple] and --brand-soft to a pale version of it.
Change the title to ["MY TOOL'S NAME"] and the subtitle underneath to [ONE SENTENCE].

Change nothing else. Give me back the whole file.

Why this one first. It cannot fail, it takes under a minute, and it proves the design tokens do what the guide says they do. Save it over a copy, open it, and you have already changed something.

Now pick a track

Same method either way. The only difference is how much you are changing at once.

Track A — one tool

Work down as far as you get. Stopping at step 2 is a good session.

1

Change what it teaches

The big one. Everything else on this page is decoration next to it.

Change it from number line jumps to [YOUR THING].

Keep the same structure: one state object, a render() that redraws everything from
scratch, inline SVG, and whole-number arithmetic so nothing rounds.

It works when I can [ONE SENTENCE — what you would do to check it].

One self-contained file, no libraries, keep the design tokens. Give me back the whole file.

Move 3 and move 4. Plain English, and a test sentence instead of a specification. You are saying what it must do, not how to build it.

2

Ask before you build

Use this instead of step 1 if you want the better version. It is the prompt that started the fraction-to-percentage tool.

I want to make an interactive I can drive on the board as a classroom teacher. It should
[WHAT IT DOES, IN TWO SENTENCES].

My plan for teaching this is [HOW YOU WOULD ACTUALLY TEACH IT — the steps, in order].

What pedagogical thoughts do you have on this idea before we build it? Ask me any
questions you need answered first.

Move 1. Nothing gets built until the thinking has been checked — the only point at which changing your mind is free. Read the answer, then say "build it".

3

Make it fit your class

One change. Ask for two and you will spend the next ten minutes untangling them.

Add [a button / a dropdown / a checkbox] that [WHAT IT SHOULD DO].

Everything else stays exactly as it is. Give me back the whole file.

One thing at a time. If it breaks, you know what broke it.

4

Say what you can see

When it comes back not quite right. Screenshot it first, then attach the screenshot with this.

See the screenshot. [WHAT IS WRONG, AS YOU SEE IT — e.g. "the labels overlap when
there are more than four", "the number line is squashed and buried under the controls"].

Fix just that. Do not change anything else.

Move 2. Point at it rather than describing it. Lead with the failing case, not a guess at the cause.

5

Check the maths

Before it goes anywhere near a class. This is the one people skip.

Look at this tool and list every input a student or I could give it that would produce
something mathematically wrong or misleading for a Year [X] class — rounding
that shows 0.30000000000000004, a recurring decimal written with an equals sign, a
divisor that can be zero, a "random" case that never comes up.

Don't fix anything yet. Just list what you find and how each one could happen.

The expensive part of you. It writes fluent code instantly, including when it is wrong. Knowing what a Year 8 needs is the half you keep.

Track B — the whole site

Download the pack, unzip it, and drag in two files: index.html from the top of the folder, and any one tool from inside it. Two files is enough for all of this — you do not need to give it the whole folder.

1

Make it my school's

This is the homepage of my maths tools site. Change the :root colour tokens to
[YOUR COLOURS, or "something that goes with my school's dark green"], change the title to
[YOUR SITE NAME], and rewrite the intro paragraph as [ONE SENTENCE ABOUT YOUR CLASSES].

Do not change the structure. That page is deliberately plain HTML with no JavaScript —
keep it that way. Give me back the whole file.

Tokens again, at site scale. Six lines change everything below them.

2

Change the sections

I don't use [worksheet creators]. Remove that section from the homepage and add one
called [YOUR SECTION] in its place, using exactly the same markup pattern as the
others. Renumber the sections and fix the item counts.

Tell me what folder I should create to match it.

Move 4. You are describing the shape of your teaching, not the HTML.

3

Add a tool and link it up

The one that makes it a site rather than a folder.

Here is my homepage and one of my existing tools.

Make me a new tool that [WHAT IT DOES — two sentences], for [STAGE AND TOPIC].
Follow the same conventions as the tool I have given you: one self-contained file, the
same design tokens, state-then-render, inline SVG for any diagram, no libraries.

It works when I can [ONE SENTENCE].

Give me back two files: the new tool, and the updated homepage with it added to the
right section. Tell me what to name the folder.

Conventions carry. Give it one file that already follows your rules and it copies them, which is why the folder convention is worth the bother.

4

Write my project brief

Do this one before you close the laptop. It is what makes the next chat fast.

Read these files and draft a CLAUDE.md for my project: what this is, how the folders are
structured, and the conventions you can see I am following — including any I have not
written down.

Flag anything where I have been inconsistent. Keep it short and high-signal.

Move 7. The project's memory between conversations. Without it you re-explain yourself every time.

5

Plan the next five

Two minutes, and you leave with a list instead of an intention.

Based on what you can see in my files, suggest five more tools I could build for
[STAGE / TOPIC]. For each one, give me a single sentence on the specific lesson it
fixes — not "a fractions tool", but the moment in a lesson where something is hard.

Don't build any of them.

Q1 from the workshop guide. If you cannot name the lesson, you will build something impressive that nobody opens.

Save over a copy, not the original. Before a big change, index-working.html is a perfectly respectable backup until you are comfortable with git. And ask for the whole file back every time — stitching a fragment into the middle of a file is where beginners lose an afternoon.

If it goes sideways

You hit a usage limit
You are on the free plan and it ran out. That is normal and it isn't you. Look at the screen next to you for the rest of the session and pick it up at home.
It gave you something huge you don't understand
“That's more than I can follow. Rewrite it as the simplest version that does only [the one thing], with a comment above each section.” Never keep code you cannot read — you will not be able to fix it in front of a class.
It keeps breaking things that worked
One change per message. If the chat has drifted, start a fresh one and paste in your brief plus the last version that worked. It costs thirty seconds.
You are stuck and can't say why
“I don't know what any of this means, walk me through it like I have never seen a computer.” Being your dumbest self is a technique, not a confession.
